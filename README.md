# mai-video-adaptive

麦麦视频理解的自适应抽帧与音频理解模块。

让视频按内容自动决定**抽多少帧、抽在哪**，配合语音转录，交给视觉模型理解。
成本压在分币级、耗时压在秒级，重复视频直接复用结果。

> 最终交付形态是麦麦插件（`plugin/`）+ 配套 NapCat 插件（`napcat-plugin/`）。

## ⚠️ 必装前置：配套的 NapCat 插件

**不装它，整条链路一行都跑不通。**

QQ 收到群视频**不会下载原片**，只存一张封面缩略图（实测 181 个视频，服务器上一个 mp4 都没有）。
而 napcat-adapter 又会把视频段压成纯文本，把下载地址丢掉。所以光靠 OneBot 接口拿不到视频。

配套的 NapCat 插件解决了这件事：监听视频消息 → 从**原始事件**里拿到真实 CDN 地址
（`multimedia.nt.qq.com.cn/...&rkey=...`）→ 用 `https` 下载到本地目录，供本插件取用。

安装步骤见 `plugin/README.md`，三步要点：放进 `napcat/plugins/`、
在 `napcat/config/plugins.json` 写 `{"video-fetch": true}`、重启 NapCat。

## 专为低消耗设计

一句话：**每一步都按“不要白花”设计，而不是把视频无脑丢给大模型。**

| 维度 | 做法 | 效果 |
|---|---|---|
| **钱** | 自适应抽帧 + 用便宜的视觉模型 | 单条视频约 **1 分钱**，月成本个位数 |
| **算力** | 帧数由内容算出来，不按固定帧率 | 重复内容 5 分钟只抽 3 帧，不浪费在重复画面上 |
| **重复开销** | 签名缓存：同一条视频再来直接复用描述 | 第二次 **0.4~0.6 秒**，跳过全部模型调用 |
| **内存** | 三道护栏：内存闸门 / 失败回退 / 用完即卸 | 4G 老机器也能安全跑本地音频 |
| **磁盘** | 理解完自动清理视频与中间文件 | 不堆文件；描述已入缓存，不影响复用 |
| **延迟** | 后台处理，不阻塞聊天；多帧一次进模型 | 约 6 秒出结果，聊天照旧 |

具体机制见下面「两条重要的工程约束」与「流程」。

## 设计原则：便宜的常驻，贵的按需

整套方案的分账口径。

理解一条视频要花钱，但花在哪、付几次，差别极大：

| 类型 | 什么时候付 | 内容 |
|---|---|---|
| **一次性** | 只在理解时付一次 | 抽帧、音频转录、视觉模型调用 |
| **常驻** | 每轮对话都在付 | 注入上下文的文本 |

所以：**重的放一次性，轻的放常驻**。

做法是把理解结果切成两份：

| 版本 | 存哪 | 体积 | 用途 |
|---|---|---|---|
| 完整时间轴 | 落盘（`<ctx.paths.data_dir>/timeline/`，即 `MaiBot/data/plugins/<插件id>/timeline/`） | 随视频长度增长 | 需要细节时按需查 |
| 压缩摘要 | 注入上下文 | **固定上限**（6 条 × 40 字 ≈ 282 字符） | 常驻，日常问答用 |

**关键在固定上限**：10 秒的视频和 10 分钟的视频，注入成本一样。

实测对比（74 秒游戏视频，19 帧）：

| | 旧：整体概括 | 初版时间轴 | 瘦身后 |
|---|---|---|---|
| 常驻注入 | 128 字符 | 525 字符 | **281 字符** |
| 一次性输出 | 78 token | 684 token | 684 token |
| 「52 秒是什么」 | 答不了 | 答得出 | 答得出 |

瘦身把常驻砍掉 46%，问答质量没掉。多付的 606 个一次性 token，换来的是「某一时刻」可以被回答。

代价说清楚：摘要压到 282 字符后覆盖变粗，细粒度问题要下沉去查本地时间轴。
省下的常驻成本，以「少数问题需要一次额外查询」的形式还回来。这就是降级链存在的意义。

## 流程

1. **签名查重**：先算视频签名，命中缓存则直接复用旧描述，跳过其余全部步骤
2. **探测**：ffprobe 读时长 + 每个 packet 的字节数（码率数据）
3. **侦察采样**：全片均匀抽一批缩略图（本地，零 API 成本）
4. **算指标**：
   - 新颖率：探针帧前后半段的覆盖度，专治重复内容
   - 码率波动：密度曲线起伏，决定帧位怎么分布
5. **定帧数**：时长 × 新颖率 → 有效内容量 → 帧数区间（含地板与硬顶）
6. **排布帧位**：按密度曲线做 CDF 撒点，密处密、疏处疏
7. **抽帧**：ffmpeg 按点抽取，等比缩小
8. **音频**：抽轨 → 静音分析 → 去静音 → 转录（三档：off / local / api）
9. **理解**：关键帧 + 语音转录 → 视觉模型 → 带时间戳的分段描述
10. **压缩**：分段描述压成固定上限的摘要（注入上下文用）
11. **入库**：描述与时间轴连同签名写入缓存

一句话分工：**签名管「要不要重做」，新颖率管「抽几张」，密度曲线管「抽在哪」，音频管「还说了什么」。**

## 依赖

- **ffmpeg / ffprobe**：必须在 PATH 中
- **Python 3.10+**
- 本地 ASR（可选）：`pip install sherpa-onnx` + SenseVoice 模型
- 视觉模型：DeepSeek API（`deepseek-flash`）

## 本地 ASR 模型

sherpa-onnx 的 SenseVoice（int8，约 228MB）：

- 模型 `model.int8.onnx`
- 词表 `tokens.txt`

放 `assets/models/` 下。实测：加载 1s，进程内存 322MB，速度 25~40 倍实时。

## 两条重要的工程约束

### 1. Prompt 缓存保护（注入位置）

视频理解的结果要注入到 bot 的模型请求里，**必须追加在上下文末尾，绝不能插在前面**。

模型开了 prompt 前缀缓存（`cache_price_in` 远低于普通输入价），命中前提是**前缀逐字节一致**。
插在前面会让每次请求的前缀都变，缓存全部失效，按全价重算、变慢；群聊消息频繁，累积开销可观。
放末尾则前缀（人设 + 历史）不动，缓存持续命中，描述照样被模型看到。

另外，麦麦这个钩子给的是它自己的 **ContextItem 列表**（不是 OpenAI messages），
返回值还必须带 `item_schema_version`，否则整包被丢弃。

### 2. 内存保护（本地音频模式的护栏）

本地推理约占 **322MB** 内存，对吃紧的机器（4G 老服务器）不友好。三道护栏，均可配：

| 机制 | 配置 | 默认 | 行为 |
|---|---|---|---|
| 内存闸门 | `audio.min_free_mb` | 500 | 加载模型前先查可用内存，不达标就不加载，直接降级 |
| 失败回退 | `audio.fallback` | true | api ↔ local 自动切换，两条都失败才放弃 |
| 用完即卸 | `audio.unload_after` | true | 转录完立即释放模型，不常驻 |

含义：即使配了本地模式，内存不够也不会把宿主挤崩；云端挂了能自动回本地。

## 三档音频模式

| 模式 | 值 | 说明 |
|---|---|---|
| 不用 | `off` | **默认**，不读音频 |
| 本地 | `local` | sherpa-onnx SenseVoice，无网络、不外传 |
| API | `api` | 云端 ASR，带超时降级 |

护栏机制见上节「内存保护」。

## 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `min_frames` / `max_frames` | `None` | 显式传入则固定；`None` 走自适应 |
| `seconds_per_frame` | 4.0 | 有效内容 → 帧数的基准（每几秒一帧） |
| `novelty_power` | 1.5 | 新颖率的倾斜力度 |
| `min_floor` / `max_cap` | 3 / 48 | 帧数地板与硬顶（成本护栏） |
| `bucket_s` | 0.5 | 密度曲线分桶粒度 |
| `max_height` | 720 | 抽帧后的最大高度 |
| `match_threshold` | 0.9 | 签名命中阈值 |
| `min_free_mb` | 500 | 本地模型内存门槛 |
| `fallback` | true | 首选途径失败时回退另一种 |
| `unload_after` | true | 转录后卸载本地模型 |
| `block_seconds` | 120 | 单块音频最长秒数（越大调用越少、越快） |
| `gap_seconds` | 6 | 语音间停顿短于此值就并成一块（越大越省调用，但多送静音） |
| `max_audio_seconds` | 600 | 只转录前 N 秒，0 表示不限（防超长视频） |

## 声画双轨

视频有两条信息轨道，都带时间戳：

| 轨道 | 来源 | 产出 |
|---|---|---|
| 画面 | 自适应抽帧 | `segments`（视觉分段描述） |
| 语音 | 分块转录（按静音切） | `audio_segments`（带时间戳的转录） |

两条轨道**分开存**（谁看到的、谁说的，各归各处），**只在摘要层合并**：

```
00:04 画面：游戏内商店界面… / 语音：「首领第一次狂暴的时候…」
```

合并时**共用同一份预算**（6 行 282 字符）：

- 只有一边有内容 → 独占整行 40 字
- 两边都有 → 各分 20 字

所以黑屏但有说话的导频不会丢内容，也不会因为多了音频就让常驻体积翻倍。

音频分块转录的做法：`silencedetect` 反推语音区间 → 小块合并成 60 秒级别的块
→ 逐块切片转录。**旧的全局去静音做法会让时间轴与原视频错位**，已弃用。

## 视频时间点问答

### 四级降级链

```
① 上下文里的压缩摘要    理解时注入，命中率最高，成本固定
② 本地完整时间轴        零模型成本，毫秒级
③ 重读视频片段          需要 keep_video = true
④ 如实说不知道          兜底，不编
```

①② 始终可用，与视频是否保留无关；③ 由配置解锁；④ 是底线。

### ③ 级：按需重读

打开配置 `timeline.keep_video` 后：

- 理解完成时把原片备份到 `data/kept_videos/<视频标识>.mp4`
- 原片按 `keep_video_hours`（默认 24 小时）自动清理
- 解锁 `read_video` 工具，参数 `video_id` / `start` / `end`

重读时不走自适应抽帧，而是在目标区间**固定密度补抽 8 帧**——区间小，要的是精度不是效率。
实测抽 8 帧耗时 **0.5~0.6 秒**（纯本地），能描述到「每秒条纹在画面哪个位置」这个粒度。

**未开保留原片时，工具对模型不可见。** 实现方式是在 `get_components` 里把它置为
禁用态，不进 planner 的视野，所以不存在「模型白调一次」的浪费。
不直接剔除组件的原因：组件未进注册表时，运行期再启用会因「未找到组件」失败，
只能重载插件恢复。保留注册、只改启用态才能热切换（配置改动后由
`_sync_read_video_state` 同步）。

### 引用提问

用户隔几小时再问时，正常人的做法是**引用那条消息**。判断依据是 reply 段里的
`message_id`（`TimelineStore.by_message` 反查），不是 @。引用时 QQ 会自动 @ 被引用者，
这个 @ 是噪音，拿它当依据会误判。

### 已知边界

- 时间轴粒度跟抽帧密度，稀疏区的问题答不细。要精确请开 `keep_video` 走重读
- 跨会话提问需要**引用原消息**。只口头说「刚才那个视频」且上下文已过期时，答不了
- 多视频歧义交给模型判断，判断不了会先反问

## 麦麦插件

`plugin/` 是可直接放进麦麦 `plugins/` 的插件。

**它有硬前置**：必须同时装一个配套的 NapCat 插件（`napcat-plugin/video-fetch/`）。
因为 QQ 不下载群视频原片、适配器又把下载地址压成了纯文本，必须从 NapCat 的
原始事件里拿真实 CDN 地址并下载。安装步骤见 `plugin/README.md` 开头的「必装前置」。

插件还带三道内存护栏（内存闸门 / 失败回退 / 用完即卸），让本地音频模式
在内存吃紧的机器上也能安全启用。

注入上下文时**一律追加在末尾**：模型开了 prompt 前缀缓存，前缀一变缓存全废，
按全价重算。详见 `plugin/README.md` 的「缓存保护」。
