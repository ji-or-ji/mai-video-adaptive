# 视频时间点问答（时间轴）

## 场景

群里有人发了视频，过了会儿问：

> 视频 10:03 那里是什么？

现有体系答不了。理解阶段只产出一段整体描述，没有时间定位，模型只能猜。

## 目标

让"某一时刻发生了什么"这类问题**有据可答**，且默认不增加理解成本。

## 四级降级链

```
① 上下文里的压缩时间轴   理解时注入，命中率最高
② 本地完整时间轴（查盘）  零模型成本，毫秒级
③ 重读视频片段           需要 keep_video = true
④ 如实说不知道           兜底，不编
```

- ①② 始终可用，与视频是否保留无关。
- ③ 由配置解锁，未开启时工具不注册，模型不会尝试。
- ④ 是底线。宁可说不知道，也不推测。

## 为什么时间轴要分两份

全量时间轴塞进上下文太贵。10 分钟视频按 10 秒粒度是 60 条、上千 token，且长期占用。

| 版本 | 存哪 | 粒度 | 用途 |
|---|---|---|---|
| 压缩版 | 注入上下文 | 粗（默认 60 秒一条） | 日常问答直接命中 |
| 完整版 | `data/video-understanding/timeline/<签名>.json` | 细（跟随抽帧密度） | 模型带时间参数来查 |

## 存储

```
<ctx.paths.data_dir>            # 实测为 MaiBot/data/plugins/<插件id>/
├── timeline/
│   └── <签名>.json        # 完整时间轴，总是写
├── timeline_index.json    # 签名 → 群 / 消息id / 时间 / 压缩版描述
└── video/                 # 仅 keep_video = true
    └── <签名>.mp4
```

注：`<ctx.paths.data_dir>` 不是 `plugins/data/`，而是 `MaiBot/data/plugins/<插件id>/`。

**key 复用已有的视频签名**：描述、时间轴、原片三份数据自动关联，不另造索引。

### timeline/<签名>.json

```json
{
  "signature": "a3f2...",
  "duration": 634.5,
  "created_at": "2026-09-13T09:20:00+08:00",
  "frame_count": 24,
  "segments": [
    {"start": 0.0, "end": 14.8, "text": "一个人在厨房切菜，右下角字幕「今日菜谱」"},
    {"start": 14.8, "end": 81.2, "text": "镜头切到户外，白色轿车驶过"}
  ]
}
```

### index.json

```json
{
  "a3f2...": {
    "group_id": "1076711748",
    "created_at": "2026-09-13T09:20:00+08:00",
    "duration": 634.5,
    "summary": "0:00 厨房切菜 → 0:15 户外车辆 → 10:00 PPT 页面",
    "video_kept": true
  }
}
```

`summary` 就是注入上下文用的压缩版，由完整时间轴按粗粒度二次归纳而来。

`message_id` 用于**按引用反查**：用户引用某条消息提问时，reply 段给出被引用消息的 id，据此定位到签名。

```json
{
  "a3f2...": {
    "group_id": "1076711748",
    "message_id": "7684674063054906249",
    "created_at": "2026-09-13T09:20:00+08:00",
    "duration": 634.5,
    "summary": "0:00 厨房切菜 → 0:15 户外车辆 → 10:00 PPT 页面",
    "video_kept": true
  }
}
```

## 配置

```toml
# 时间轴问答
timeline_enabled = true        # 总开关，关掉则退回原行为
context_granularity = 60       # 注入上下文的粒度（秒）
timeline_ttl_days = 7          # 时间轴保留天数
timeline_max_entries = 200     # 条数上限，超出按时间淘汰

# 精确重读（继承现有视频保留配置）
keep_video = false             # 默认关闭。开启才注册重读工具
keep_video_hours = 24
```

## 改动点

| 文件 | 改动 |
|---|---|
| `adaptive_frames.py` | 理解阶段 prompt 增加时间戳输出要求；`understand_video()` 返回结构从纯文本改为 `{summary, segments}` |
| 新增 `timeline_store.py` | 时间轴的读写、签名索引、TTL 淘汰、压缩版生成 |
| `plugin.py` | 理解完成后写入时间轴；注入时改用压缩版并带 `视频#<签名>` 标识；`keep_video` 决定是否删原片 |
| 工具注册 | `keep_video = true` 时注册 `read_video`，参数 `video_id` / `start` / `end` |

## 注入格式

上下文里带可引用标识，模型才知道能问哪条视频：

```
[视频#a3f2 内容摘要]
0:00 厨房切菜 → 0:15 户外车辆 → 10:00 PPT 页面（标题「第三季度营收」）
如需细节可询问具体时间点。
```

标识的作用有二：让模型知道"有这条视频"；给工具提供 `video_id` 参数来源。

## ③ 精确重读的实现要点

抽帧是**按密度撒点**，不保证 10:03 恰好有帧。所以：

1. 取 10:03 前最近的已抽帧作为锚点
2. 在 `10:03 ± 15s` 区间**固定密度补抽**（区间小，要精度不要效率）
3. 连同原问题一起交给模型，prompt 要求**完整描述区间画面**，不猜用户在指什么（10:03 可能是物体、字幕、一句话）

## 已定（三个歧义问题的结论）

### 1. 粒度不自洽 → 不处理

时间轴跟抽帧密度走，疏密不均。落在稀疏区的问题，精度天然有限（可能只有一条跨 2 分钟的粗描述）。

**结论：接受这个代价，不做最大段长兜底。** 本插件的卖点是节省 token，为泛需求补精度会牺牲整体。精度不够时走 ③ 重读，或如实说明。

### 2. 跨会话引用 → 靠引用消息

用户隔几小时再问，上下文里早没有 `视频#a3f2` 标识。正常人的做法是**引用那条消息**再问。

**判断依据是 reply 段里的 message_id**，不是 @。引用消息时 QQ 会自动 @ 被引用者，这个 @ 是噪音，拿它当依据会误判。

```
[引用 视频#a3f2] 10:03 那里是什么意思？
```

侧写：bot 看不到引用的具体内容时，用户会**引用 + 重复强调**，引用本身就是最强的定位信号。

### 3. 多视频歧义 → 模型自己判断

同一群短时间内发两条，用户说"那个视频"。不做消歧逻辑，交给模型按上下文判断。判断不了就问，不猜。

## 已知边界（写进 README）

- 时间轴粒度跟抽帧密度，稀疏区的问题答不细。要精确请开启 `keep_video` 走重读
- 跨会话提问需要**引用原消息**。只口头说"刚才那个视频"，且上下文已过期时，答不了
- 多视频歧义交给模型判断，可能答错，会先反问

## 实现顺序

1. 时间轴产出 + 落盘（不注入，先看数据质量）
2. 压缩版注入上下文（①②生效）
3. `keep_video` 与重读工具（③）
